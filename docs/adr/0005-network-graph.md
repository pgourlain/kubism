# ADR 0005: Network graph, how exposure is derived and what is not visible

Status: accepted. Date: 2026-10.

## Context
Kubism shows how traffic reaches the pods: exposure → Ingress → Service → workload, with ports on every hop. "Public" means reachable from outside the cluster, which the cluster's own objects can say; guessing from IP ranges or annotations cannot be right.

## Decision
`NetworkGraph` (`Kubism.Core/Network`) is a pure, immutable model built from Ingresses, IngressClasses, Services, EndpointSlices and Pods (and, where installed, Gateway API objects, see below). `NetworkStore` keeps it current through the session's `ResourceCache` (five shared informers, plus one per Gateway API kind the cluster serves); `NetworkLoader` builds one for the MCP server. Read-only: nothing goes through `ClusterActions`.

**Exposure levels** (`ExposureLevel`):
* **Outside the cluster:** a Service of type `LoadBalancer` or `NodePort`, or with `externalIPs`; an Ingress whose controller's Service is such a Service; an ingress controller that runs outside the cluster (Azure Application Gateway / AGIC, AWS ALB, GCE); pods with `hostPort` or `hostNetwork`. An internal cloud load balancer (annotations such as `azure-load-balancer-internal`) is outside the cluster too: it only adds the note "private network".
* **In-cluster only:** everything else. An Ingress whose controller Service is `ClusterIP` is in-cluster, and the graph says so.
* **Unknown:** the Ingress has no class, or its controller's Service cannot be found. Flagged as a problem; never presented as in-cluster or outside.
The level flows from the exposure nodes along the edges (the highest wins), so a Service reached by an exposed and an unexposed Ingress is outside overall while each Ingress keeps its own level.

**Finding the controller.** Through `IngressClass.spec.controller` (or the `kubernetes.io/ingress.class` annotation, or the default class), mapped to the controller's Service by the labels each controller's chart sets (`ingress-nginx`, `nginx-ingress`, `traefik`, `haproxy-ingress`, `contour`/`envoy`, Istio `ingressgateway`). When several controllers of one kind exist (public and internal), the one whose Helm instance is named after the class wins, else the one whose name contains it. Admission and metrics Services are never taken for the controller. The controller's Service is drawn as the exposure node, not as a Service chain.

**Ports.** Ingress backend port (number or name) → Service port → `targetPort` (a name is resolved against the selected pods' container ports) → container port. Workloads come from the pods' owner chain; a Deployment is recognised from its ReplicaSet's `pod-template-hash`, a CronJob from its Job's name, without reading ReplicaSets or Jobs.

**Routes.** Every host + path an Ingress serves is also a row (`NetworkRouteRow`): `https` when a `spec.tls` entry covers the host, the controller and address it comes in through, the backend Service port, the workloads behind it with the port mapping, and the problems of the Ingress and the Service. This is the answer to "which URL goes through which Ingress"; the graph is the picture of the same data.

**Problems** are put where the fault is: a missing backend Service or port on the Ingress and the hop (not on a Service that serves other Ingresses fine); an unresolved named `targetPort` on the Service and the hop; no ready endpoint / selector matching no pod on the Service; pods not ready on the workload; missing or expiring TLS secret on the Ingress; no ingress class or no controller found on the Ingress; a Service exposed directly (not through an Ingress) and host ports.

**TLS secrets** are looked up one by one (`GET`, cached 5 minutes): only existence and the public certificate's expiry are read, and nothing of the secret is kept (rule 4). A secret that cannot be read (403) is "not checked", never "missing".

**Namespace filter.** A chain is kept when its Ingress, Service or workload is in a chosen namespace. Exposure nodes of another namespace (the controller's Service) stay as dimmed context, so the path to the outside is never cut, but the other chains they feed are not pulled in. Services nothing routes to are hidden unless asked for, except when looking for problems.

**Nodes.** With "Show nodes" a fifth column shows the nodes the pods run on, one box per node shared by the workloads that have a pod there, from `spec.nodeName`. Node status (Ready, cordoned) comes from the node list, which is optional: when it cannot be read the boxes say "status unknown" and the graph is not reported incomplete. The exposure level does not flow to a node (where a pod runs says nothing about how it is reached), and a node problem does not make a chain a problem chain. Workload details list the nodes either way.

**Gateway API (second batch, 2026-11).** Where the cluster serves `gateway.networking.k8s.io`, a Gateway is a chain source next to the Ingress: it takes the Ingress column (a node of kind `Ingress` with `Flavor = "Gateway"`, so the layout, filters, namespace rule and Routes table need no second path), its **listeners** are drawn in its box, and each route attached to it becomes edges to the backend Services and rows in the Routes table (`NetworkRoute.RouteName`, class = GatewayClass). The kinds are read through `GatewayApi.Find` from discovery, each at its best served version (`v1`, then `v1beta1`, `v1alpha3`, `v1alpha2`); a cluster without the CRDs adds no informer and no warning, a kind that cannot be listed is reported like any other.
* **Exposure** comes from the controller that implements the Gateway. `GatewayClass.spec.controllerName` says who it is: Azure Application Gateway for Containers (`alb.networking.azure.io`), AWS VPC Lattice and GKE Gateway run outside the cluster. For the others the controller's Service is found by the labels controllers put on what they create for a Gateway (`gateway.networking.k8s.io/gateway-name`: Istio, NGINX Gateway Fabric; Envoy Gateway's `owning-gateway-*`; Cilium's `io.cilium.gateway/owning-gateway`), or, for one shared Service (Traefik, Kong, older NGINX Gateway Fabric), by its usual name label. The Service is the exposure node, as for an Ingress; `Gateway.status.addresses` is shown, not used to decide the level. No Service found = *Unknown*.
* **Routes.** `HTTPRoute`, `GRPCRoute`, `TLSRoute`, `TCPRoute` and `UDPRoute` are matched to a Gateway by `parentRefs` (group, kind, name, namespace; `sectionName` and `port` pick the listeners, and only compatible listeners count: an `HTTPRoute` does not land on a `TCP` listener). Hostnames are the route's, else its listeners'. A rule gives one edge per backend Service (weights shown), one row per host × match (path prefix, `=` exact, `~` regular expression, method and header matches noted; gRPC service/method; the listener port for TLS/TCP/UDP routes, with `tcp://*:5432`-style URLs). Only Services are followed; another `backendRef` kind is noted, not drawn.
* **What the controller said is used when it said something.** A route's `status.parents` (`Accepted`/`ResolvedRefs` False), a Gateway's `Accepted`/`Programmed`, its listeners' conditions and the GatewayClass's `Accepted` become problems with the controller's own reason and message. When a route has no status for a Gateway, the listener's `allowedRoutes.namespaces.from: Same` is checked against the route's namespace (a `Selector` cannot be evaluated: no namespace labels are read, so it is assumed to allow).
* **Cross-namespace references** (a route to a Service of another namespace, a listener to a Secret of another namespace) need a `ReferenceGrant` in the target namespace whose `from` names the group, kind and namespace of the referrer and whose `to` names the Service or Secret (or all of that kind). A missing grant is a `reference-not-permitted` problem on the Gateway and the hop; a grant for `HTTPRoute` does not cover a `GRPCRoute`.
* **TLS.** Listener `certificateRefs` are looked up like Ingress secrets (existence and expiry only); passthrough listeners have no certificate to check; a terminating listener with no `certificateRef` is a problem.
* **Other problems:** GatewayClass missing or not accepted, no route attached ("serves nothing", low), a route with no compatible listener, a missing backend Service or port.
* Usage: a Gateway uses its GatewayClass and its TLS Secrets, a route uses its backend Services; a class nobody uses is *Not referenced*, a class, certificate or backend that does not exist is a broken reference.
* Discovery had to change for this: it read only the preferred version of each group, so a kind served only by an older version (`ReferenceGrant` v1beta1, `TCPRoute` v1alpha2) was invisible. It now lists a resource at the first version that serves it.

**Incomplete data is stated:** a kind that cannot be listed (typically 403) is named in a banner and in the MCP answer instead of a silently partial graph.

## Not visible (known limits)
* DNS, firewalls, network security groups, WAF, Front Door, service mesh policy and cloud load balancer rules.
* **NetworkPolicy** (what is blocked even though a path exists) is not read yet.
* Gateway API: `BackendTLSPolicy`, `ListenerSet`, filters (redirects, rewrites, mirrors), header/query matches beyond a count, `ReferenceGrant`s for kinds other than Service and Secret, namespace selectors in `allowedRoutes`, hostname intersection between a route and its listener, and implementation-specific resources (Envoy Gateway's `SecurityPolicy`, Istio's `VirtualService`) are not evaluated. Istio's own `networking.istio.io` Gateway is another group and is not read.
* A controller whose Service does not carry the usual labels is reported as "controller not found" (exposure unknown); there is no per-class override yet.
* Ingress backends that are `resource` references (not Services) are ignored.
* Tests: the fixture (`Data/network.yaml`) is hand-built from the usual shapes of ingress-nginx, AGIC and Traefik; it has not been compared with real AKS clusters yet (manual validation in tasks.md).
